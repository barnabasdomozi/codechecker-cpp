# Reference: background tasks and `CodeChecker cmd serverside-tasks`

Usage: [../usage/cmd-serverside-tasks.md](../usage/cmd-serverside-tasks.md)

Python source: `codechecker_api/tasks.thrift`,
`web/server/codechecker_server/api/tasks.py`,
`web/server/codechecker_server/task_executors/{task_manager,abstract_task,main}.py`,
`web/server/codechecker_server/database/config_db_model.py`
(`BackgroundTask`), `web/client/codechecker_client/task_client.py`,
`web/client/codechecker_client/cli/cmd.py` (`__register_tasks`).

The only real task kinds in 6.30.0 are the stores
(`report_server::massStoreRunAsynchronous()` and
`report_server::massStoreRun()`, [store.md](store.md)). A testing-only kind
`TaskService::DummyTask` exists (§3.4).

## 1. Task record

Stored in the config DB table `background_tasks`
([server-database.md](server-database.md) §4.1):

| Field | Meaning |
|---|---|
| `token` | 64 random lowercase hex characters (unique; up to 10 retries on collision) |
| `machine_id` | the server's machine id ([server.md](server.md) §1) |
| `kind`, `summary` | type name and human-readable summary |
| `status` | `allocated` → `enqueued` → `running` → `completed` / `failed`; or `cancelled` / `dropped` |
| `product_id` | associated product or NULL (server-wide) |
| `username` | creator (`Anonymous` for stores on servers without authentication) |
| `comments` | appended text log (§1.1) |
| `enqueued_at`, `started_at`, `finished_at`, `last_seen_at` | UTC timestamps (stored without zone) |
| `consumed` | the creator has read the final status |
| `cancel_flag` | cancellation requested |

Transitions (any other transition is an error):
- create → `allocated`, `last_seen_at = now`;
- enqueue: `allocated` → `enqueued`, `enqueued_at = now`;
- start: `enqueued` → `running`, `started_at = now`;
- finish: `running` → `completed` or `failed`, `finished_at = now`;
- abandon: → `cancelled` if `cancel_flag` is set and not forced, else
  `dropped`; `finished_at = now`.

"Terminated" = not `allocated`/`enqueued`/`running`. Heartbeat sets
`last_seen_at = now` while `enqueued` or `running`.

### 1.1 Comments

`add_comment(text, actor)` appends

```
[\n----------\n]<actor or "<unknown>"> at <UTC time with +00:00>:\n<text>
```

(the separator only if comments already exist). System texts used:
`WARNING!\nExecuting a legacy 'massStoreRun()' API call!` (actor
`SYSTEM`), `CANCEL!\nTask cancelled before execution began!`,
`CANCEL!\nCancel request of admin honoured by task.`,
`SHUTDOWN!\nTask honoured graceful cancel signal generated by server shutdown.`,
`FAILED!\nException during execution:\n<message>` (actors
`SYSTEM[AbstractTask::execute()]`), `SHUTDOWN!\nTask never started due to
the server shutdown!` and `DROPPED!\n<reason>` (actor `SYSTEM`),
`User requested cancellation.` (actor = the user).

## 2. Execution

- The API process allocates the record, prepares input data in
  `<workspace>/codechecker_tasks/<machine id, characters '"<>:\/|*?.
  and space replaced by _>/<token>-<random>/`, enqueues the task object on a
  queue shared with the task worker processes, and creates a pipe for
  "done" notification (used by the synchronous `massStoreRun`).
- A task worker pops tasks (1 s poll) and executes:
  1. if cancellation is due (§2.1): comment + abandon (→ `cancelled`), done;
  2. set `running` (database error → force `dropped`);
  3. run the task body; success → `completed`;
     cancellation honoured → abandon with comment (`cancelled`, or `dropped`
     during shutdown); other exception → ERROR log + `FAILED!` comment →
     `failed` (the status write is retried up to 10 times with exponential
     back-off);
  4. always delete the input data and signal "done".
- Cancellation is cooperative: the body checks at safe points
  (`heartbeat` + `should_cancel`). `should_cancel` = the server is shutting
  down, or status is `enqueued`/`running` and `cancel_flag` is set.
- Server start: every task of the same machine id still in
  `allocated`/`enqueued`/`running` gets `DROPPED!\nNew server started with
  the same machine_id, assuming the old server is dead and won't be able to
  finish the task.` and status `dropped`; the whole task data directory of
  the machine id is deleted.
- Server shutdown: task workers stop taking tasks; queued tasks seen within
  5 s get `SHUTDOWN!...never started...` and `dropped`; after the workers
  exited, remaining non-terminated tasks of the machine id get
  `DROPPED!\nServer shut down, task will be never be completed.`

## 3. API (`/v6.74/Tasks`)

Timestamps in the API are integer Unix epochs (UTC); 0/unset = none.

### 3.1 `getTaskInfo(token)` → `TaskInfo`

`{token, taskKind, status (enum), productId (0 if none), actorUsername,
summary, comments, enqueuedAtEpoch, startedAtEpoch, completedAtEpoch,
lastHeartbeatEpoch, cancelFlagSet}`.

Allowed if:
- the caller's user name equals the task's `username` (the caller is
  `None` without a session, so on servers without authentication this never
  matches `Anonymous`); then, if the task is terminated, `consumed` is set
  to true;
- else, task has a product: caller has `PRODUCT_ACCESS` on it (the IDL
  comment says PRODUCT_ADMIN);
- else (server-wide task, or the token does not exist): caller has
  `SUPERUSER`.

Not allowed → `UNAUTHORIZED "The task does not exist, or you are not
authorized to view the task. (Only the task's submitter, people with access
to the task's product, or a SUPERUSER can view the task.)"`. Allowed but
missing → `GENERAL "The task does not exist."`

### 3.2 `getTasks(TaskFilter)` → `list<AdministratorTaskInfo>`

`AdministratorTaskInfo = {normalInfo: TaskInfo, machineId, statusConsumed}`.
Does not set `consumed`.

Pre-checks: `productIDs` = empty list (server-wide tasks) needs
`SUPERUSER` (`UNAUTHORIZED "Querying service tasks (not associated with a
product) requires SUPERUSER privileges!"`); each listed product needs
`PRODUCT_ACCESS` (`UNAUTHORIZED "Querying product tasks requires
PRODUCT_ACCESS rights, but it is missing from product(s): '<ep>', ..."`).

Conditions (AND of fields; OR within a list):

| Field | Condition |
|---|---|
| `tokens`, `machineIDs`, `kinds` | column ILIKE value with `*` → `%` (so `%`/`_` are wildcards too; case-insensitive) |
| `statuses` | status in list |
| `usernames` unset / `[]` / list | no condition / `username IS NULL` / ILIKE any |
| `productIDs` unset / `[]` / list | no condition / `product_id IS NULL` / in list |
| `enqueuedBefore/After`, `startedBefore/After`, `completedBefore/After`, `heartbeatBefore/After` | `<=` / `>=` on the column (0 = no condition) |
| `cancelFlag`, `consumedFlag` (`Ternary`) | `BOTH`(0) none, `OFF`(1) false, `ON`(2) true |

Then rows are filtered by visibility: server-wide tasks only for
`SUPERUSER`, product tasks only with `PRODUCT_ACCESS` on that product.
Order: database order (unspecified).

### 3.3 `cancelTask(token)` → bool

Allowed for the task's creator (same name rule as §3.1), else
`PRODUCT_ADMIN` of the task's product, else `SUPERUSER`
(`UNAUTHORIZED "The task does not exist, or you are not authorized to
cancel the task. (Only the task's submitter, people with PRODUCT_ADMIN on
the task's product, or a SUPERUSER can cancel the task.)"`; missing →
`GENERAL "The task does not exist."`). Returns false if the task is
terminated or already flagged; otherwise adds the comment `User requested
cancellation.`, sets `cancel_flag` and returns true.

### 3.4 `createDummyTask(timeout, shouldFail)`

Only if the server's environment has `TEST_WORKSPACE`
(else `GENERAL "createDummyTask() is only available in testing
environments!"`): a server-wide task that ticks once per second up to
`timeout`, honours cancellation and fails at the end if `shouldFail`.

## 4. Waiting for a task (`await_task_termination`)

Used by `store` and `--await`:

- Poll `getTaskInfo(token)`; stop when the status is `COMPLETED`,
  `FAILED`, `CANCELLED` or `DROPPED`, and return its name.
- A failed call (any error that makes the call wrapper exit) is retried:
  INFO `Retrying task status query [<n> / 10 retries] ...`; after more than
  10 consecutive failures the error ends the program (exit 1).
- "Last progress" = `completedAt`, else `lastHeartbeat`, else `startedAt`.
  If known and at least 1 hour ago → ERROR `'1:00:00' timeout elapsed since
  task last progressed at '<time>', considering hung/locked out/lost/failed...`
  and a `TaskTimeoutError` (traceback, exit 1).
- Wait between polls starts at 5 s. Once progress timestamps are known:
  no change since the previous poll → +1 s; changed by at most twice the
  current wait → halve it; otherwise +1 s; clamped to 5 s … 120 s. (Before
  the first progress timestamp the wait stays 5 s.)

## 5. `CodeChecker cmd serverside-tasks`

```
CodeChecker cmd serverside-tasks [-t/--token [TOKEN ...]] [--await] [--kill]
    [--output {plaintext,table,json}]
    [--machine-id [ID ...]] [--type [KIND ...]]
    [--status [{allocated,enqueued,running,completed,failed,cancelled,dropped} ...]]
    [--username [U ...] | --no-username] [--product [EP ...] | --no-product]
    [--enqueued-before TS] [--enqueued-after TS] [--started-before TS]
    [--started-after TS] [--finished-before TS] [--finished-after TS]
    [--last-seen-before TS] [--last-seen-after TS]
    [--only-cancelled | --no-cancelled] [--only-consumed | --no-consumed]
    [--url SERVER_URL] [--verbose L]
```

`TS` = `year:month:day[:hour[:minute[:second]]]` (missing parts 0),
interpreted as **UTC**. Default `--output plaintext`. Logging to stderr
unless `table`.

### 5.1 Building the filter

A filter object is created as soon as any filter option is given; then:

| Option | `TaskFilter` |
|---|---|
| `--machine-id`, `--type` | `machineIDs`, `kinds` (empty values → no condition) |
| `--status` | `statuses` (upper-cased enum) |
| `--username U...` | `usernames` |
| `--product EP...` | `productIDs`: for each endpoint, `Products.getProducts(EP, null, ...)` and the product whose endpoint equals EP exactly; not found → WARNING `No product with endpoint '<EP>', omitting it from the query.` (if none are found the list is empty → server-wide tasks only) |
| `--enqueued-*`, `--started-*`, `--finished-*` | the matching epoch fields |
| `--only-/--no-cancelled`, `--only-/--no-consumed` | `cancelFlag`/`consumedFlag` = `ON`/`OFF` |

⚠️ Bugs in 6.30.0 (verified):
- `--no-username` and `--no-product` set attributes that are not part of
  `TaskFilter`; they are ignored (the intended meaning is `usernames = []`
  / `productIDs = []`);
- `--last-seen-before`/`--last-seen-after` send the `--started-before`/
  `--started-after` values (none if those are absent), so they have no
  effect on their own.

### 5.2 With a filter

`tokens` = the `-t` values; `getTasks(filter)`. Product ids are mapped
back to endpoints (from the lookups above, else via `getProducts`).

- `json`: list of flat objects: `machineId`, `statusConsumed`, then the
  `TaskInfo` fields with `status` as its name, epoch fields renamed
  (`enqueuedAt`, `startedAt`, `completedAt`, `lastHeartbeat`) and
  formatted `YYYY-MM-DD HH:MM:SS` (UTC) or null, and `productId` replaced
  by `productEndpoint` (null for server-wide). One line.
- otherwise (`plaintext` behaves as `table`): header
  `Token, Machine, Type, Summary, Status, Product, User, Enqueued, Started, Last seen, Completed, Cancelled?`
  with empty cells for nulls and `Yes` if the cancel flag is set.

### 5.3 Without a filter

No `-t` either → ERROR `ERROR! To use 'CodeChecker cmd serverside-tasks',
a '--token' list or some other filter criteria **MUST** be specified!`,
exit 2.

Otherwise `getTaskInfo` for each token (errors → exit 1 via the call
wrapper). Output:
- `json`: list of flat objects as above without the admin fields;
- one task and `plaintext`:

  ```
  Task '<token>':
      - Type:         <kind>
      - Summary:      <summary>
      - Status:       <STATUS>
      - Product:      <endpoint or None>
      - User:         <user>                 (only if set)
      - Enqueued at:  <time or empty>
      - Started at:   <time or empty>
      - Last seen:    <time or empty>
      - Completed at: <time or empty>
      - Cancelled by administrators!         (only if flagged)

  ```
  then, if there are comments, `Comments on task '<token>':` and an empty
  line, and each comment line: empty lines and `----------` as is, header
  lines (containing ` at ` and ending in `:`) as is, others prefixed with
  `> `;
- several tasks or `table`: header
  `Token, Type, Summary, Status, Product, User, Enqueued, Started, Last seen, Completed, Cancelled by administrators?`.

Exit code for exactly one token (without `--await`): `COMPLETED` 0,
`FAILED` 4, `ALLOCATED`/`ENQUEUED`/`RUNNING` 8, `CANCELLED`/`DROPPED` 16.

### 5.4 `--kill` and `--await`

Applied to the matched tasks (filter mode) or the given tokens:

1. `--kill`: `cancelTask` for each; true → INFO `Submitted cancellation
   request for task '<token>'.`; false → debug only.
2. `--await`: exit code starts at 0; for each token INFO `Awaiting the
   completion of task '<token>' ...` and wait (§4). `COMPLETED` → INFO
   `Task '<t>' terminated in status: COMPLETED.`; with `--kill`,
   `CANCELLED` → INFO `Task '<t>' terminated in status:  CANCELLED.` (two
   spaces); any other status → ERROR `Task '<t>' error status: <S>!` and exit
   code 1.

Without `--await`, the exit code is the one of §5.3 (single token) or 0.
