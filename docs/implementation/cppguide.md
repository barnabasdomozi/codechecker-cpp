# C++ coding guideline

**Mandatory.** Every C++ file written for this project must follow this
guideline at all times. It is the only coding guideline of the project; other
documents do not add or override coding rules.

This guideline is based on the Google C++ Style Guide, rewritten as a list of
rules; this file is complete on its own. The rules are the guide's decisions; its
explanations (definitions, pros and cons) are left out. Abseil, Protocol
Buffers and other Google-internal tools are not used in this project, so
rules that name them are given with the standard C++ equivalent. The rules for
Windows code are left out because the project is Linux only.

**Scope.** All C++ code under `src/` and `tests/`. It does not apply to code
copied unchanged from the Python repository (`ldlogger/`, `web-ui/`) or to
code generated by the Thrift compiler; see
[Existing non-conformant code](#24-existing-non-conformant-code).

**Waivers.** Three decisions of this project differ from the original guide.
They are listed in [Project waivers](#project-waivers) and are part of this
guideline; the rules below already include them.

**How to use it.** Rules are written as **must** / **must not** (no
exceptions without a recorded waiver), **should** / **prefer** (the default;
deviate only with a reason you can state in a comment or review), and **may**
(allowed). When this guide does not cover a case, follow the code around you;
when there is none, choose what is clearest for a reader who does not know the
code.

## Project waivers

These are the only deviations from the original guide. New waivers are added
here, nowhere else.

- **W1. Exceptions only at the Thrift boundary.** Apache Thrift's C++ library
  and generated code use exceptions, so exceptions are allowed only where the
  code meets Thrift:
  - API handler classes (`src/server/api/`) report errors by throwing the
    generated exception types (`RequestFailed`), as the Thrift interface
    requires;
  - the server's request dispatch catches the exceptions that a Thrift
    processor call can raise (`apache::thrift::TException`, and
    `std::exception` from the standard library) and turns them into a
    `TApplicationException` reply;
  - the client's Thrift transport (`src/client/transport/`) may throw
    `TTransportException` to report a failed HTTP request, as `TTransport`
    requires, and the client call wrapper catches the exceptions of generated
    client calls.

  No exception may leave these places. Code they call follows the normal
  rule: no exceptions, errors are returned as values.
- **W2. `<filesystem>` is allowed.** `std::filesystem` may be used. Because
  the project does not use exceptions, call only the overloads that take a
  `std::error_code&` and check it; **never** call the throwing overloads.
- **W3. The top-level namespace is `cc`.** All project code is in namespace
  `cc` and one nested namespace per library (`cc::report`, `cc::server`, ...).
  Header guards and exported macros use the prefix `CC_`.

## 1. Principles

These explain the rules and decide cases the rules do not cover.

- **Optimize for the reader, not the writer.** Code is read far more often
  than it is written. When something surprising happens (for example, an
  ownership transfer), make it visible at the point of use.
- **Be consistent with existing code**, most of all within a file and a set of
  related interfaces. Consistency is not a reason to keep an old style when a
  rule says otherwise.
- **Be consistent with the broader C++ community** where the standard or a
  well-known idiom solves the problem, unless a rule below restricts it.
- **Avoid surprising or dangerous constructs.**
- **Avoid constructs an average C++ programmer would find tricky or hard to
  maintain.** The absence of a prohibition is not permission for clever or
  unusual code.
- **Optimize for performance only when needed**; then a rule may yield, with
  a comment saying why.

## 2. C++ version

- Code **must** target **C++20**. C++23 features **must not** be used, even
  where the compiler supports them.
- Non-standard extensions **must not** be used (see
  [§14](#14-libraries-and-extensions)).

## 3. Header files

**Files**

- Every `.cc` file **should** have a matching `.h` file. Exceptions: unit
  tests and small `.cc` files that only contain `main()`.
- Headers **must** end in `.h` and be **self-contained**: they compile on
  their own, have a `#define` guard and include everything they need.
- Files meant for textual inclusion at an unusual place (not self-contained)
  **must** end in `.inc`. Use them rarely.
- Definitions of inline functions and templates that clients instantiate
  **must** be in the header (or in files it includes). **Do not** use
  separate `-inl.h` files. A template used only in one `.cc` file may be
  defined there.

**`#define` guard**

Every header **must** have a guard named `CC_<PATH>_<FILE>_H_` (W3), based
on the full path from the source root (`src/` itself is left out):

```cpp
// src/report/model/report.h
#ifndef CC_REPORT_MODEL_REPORT_H_
#define CC_REPORT_MODEL_REPORT_H_

...

#endif  // CC_REPORT_MODEL_REPORT_H_
```

**Include what you use**

- A file **must** directly include the header that declares every symbol it
  uses. **Do not** rely on transitive includes (this also applies between
  `foo.cc` and `foo.h`).
- **Do not** include headers for any other reason.

**Forward declarations**

- **Avoid** forward declarations; include the header instead.
- **Never** forward-declare entities your project does not own (including
  anything in `std`).
- For your own entities, make headers cheap to include. Use a forward
  declaration only when your judgment is that it is the best fix for a real
  compile-time problem.

**Functions defined in headers**

- Define a function at its public declaration only if it is short (about 10
  lines or fewer). Put longer bodies in the `.cc` file unless they must be in
  the header.
- A definition that must be in the header but is not short goes in an
  internal part: the `private` section of a class, a namespace containing
  `internal`, or below a `// Implementation details only below here` comment.
- Every definition in a header **must** be ODR-safe: `inline`, a template, or
  defined in the class body.

**Include names and order**

- Include project headers by their path from the source root, without `.` or
  `..`: `#include "report/model/report.h"`.
- Use angle brackets only where required: C and C++ standard headers, POSIX
  and Linux system headers, and third-party libraries that require them.
- Order, with one blank line between non-empty groups, alphabetical inside
  each group:
  1. the related header (`foo.h` for `foo.cc` or `foo_test.cc`);
  2. C system headers and other angle-bracket headers ending in `.h`
     (`<unistd.h>`, `<sys/types.h>`, `<curl/curl.h>`);
  3. C++ standard library headers (`<string>`, `<vector>`);
  4. other libraries' headers;
  5. this project's headers.
- `<stddef.h>` and `<cstddef>` styles are both acceptable; be consistent with
  the surrounding code.
- System-specific conditional includes may go after the other includes.

```cpp
#include "server/http/router.h"

#include <sys/types.h>
#include <unistd.h>

#include <string>
#include <vector>

#include "server/api/report_handler.h"
#include "util/json/writer.h"
```

## 4. Scoping

**Namespaces**

- Code **must** be in a namespace (with few exceptions such as `main()`):
  `cc` and the library's nested namespace (W3), possibly followed by more
  levels based on the path.
- **Must not** use using-directives (`using namespace foo;`).
- **Must not** use inline namespaces.
- **Must not** declare anything in namespace `std`.
- Namespaces wrap the whole file after the includes and forward declarations.
  End multi-line namespaces with a comment: `}  // namespace cc::report`.
- Namespace aliases **must not** be at namespace scope in headers, except in
  namespaces explicitly marked internal. They are fine in `.cc` files and
  inside functions.
- Use a namespace with `internal` in its name for API parts users must not
  touch, unique per library file (`cc::report::internal_plist`, not just
  `cc::report::internal`).
- Prefer single-line nested declarations: `namespace cc::report {`.

**Internal linkage**

- Definitions in a `.cc` file that are not used elsewhere **should** have
  internal linkage: an unnamed namespace or `static`.
- **Must not** use unnamed namespaces or `static` linkage in headers.
- Format an unnamed namespace like a named one; the closing comment is
  `}  // namespace`.

**Nonmember, static member and global functions**

- Prefer nonmember functions in a namespace; global functions should be rare.
- **Do not** create classes that only group static members. Valid reasons for
  static members: policy classes, traits, type semantics for a separate
  representation, closing an interface to extension.
- Nonmember functions **should not** depend on external variables. If one is
  only used in its `.cc` file, give it internal linkage.

**Local variables**

- Declare variables in the narrowest scope, close to first use, and
  initialize them in the declaration (`int i = f();`, not `int i; i = f();`).
- Prefer brace initialization for containers: `std::vector<int> v = {1, 2};`.
- Declare variables used only by an `if`, `while` or `for` inside the
  statement: `while (const char* p = strchr(str, '/')) str = p + 1;`.
- Exception: an object with an expensive constructor/destructor used in a
  loop may be declared before the loop.

**Static and global variables**

- Objects with static storage duration (globals, static members, function
  `static`s) **must** be **trivially destructible**. Rule of thumb: the
  declaration could be `constexpr`.
  - Allowed: `const int kNum = 10;`, arrays of trivial structs,
    `static const char* const kMessages[] = {...};`,
    `constexpr std::array<int, 3> kArray = {1, 2, 3};`.
  - Not allowed: `const std::string kFoo = "foo";`,
    `static std::map<int, int> kData = ...;`, static smart pointers.
- Constant initialization of static variables **should** be marked
  `constexpr` or `constinit`. A non-local static without either is assumed to
  have dynamic initialization and needs careful review.
- Dynamic initialization of non-local variables is forbidden unless nothing
  in the program depends on its order relative to other initializations
  (`int p = getpid();` is allowed if no other static uses `p`).
- Dynamic initialization of function-local statics is allowed.
- Patterns:
  - string constants: `constexpr std::string_view`, a character array or a
    `const char*` to a literal;
  - fixed lookup tables: arrays of trivial types (pairs of `int` and
    `const char*`, ...), searched linearly or kept sorted for binary search;
  - custom constant types: give them a trivial destructor and a `constexpr`
    constructor;
  - if nothing else works: a function-local static pointer or reference that
    is never deleted: `static const auto& impl = *new T(args...);`.

**`thread_local`**

- `thread_local` at namespace or class scope **must** be initialized with a
  compile-time constant and marked `constinit`:
  `constinit thread_local Foo foo = ...;`.
- Function-local `thread_local` has no initialization restriction; use a
  function returning a reference to it to emulate a namespace-scope one.
- Prefer trivially destructible `thread_local` types; a destructor must not
  touch other (possibly destroyed) `thread_local`s.
- Prefer `thread_local` over other ways of making thread-local data.

## 5. Classes

**Work in constructors**

- Constructors **must not** call virtual functions.
- Avoid initialization that can fail when you cannot signal the error.
  Terminate the program if that is the right response; otherwise use a
  factory function (or an `Init()` method). Avoid `Init()` on objects that
  have no other states affecting which methods may be called.

**Implicit conversions**

- Conversion operators and constructors callable with one argument **must**
  be `explicit`.
- Exceptions: copy and move constructors are not `explicit`; a constructor
  taking a single `std::initializer_list` omits `explicit`; constructors that
  cannot be called with one argument may omit it.
- Implicit conversions between types that are different representations of
  the same value need a recorded waiver.

**Copyable and movable types**

- Every class's public API **must** make clear whether it is copyable,
  move-only, or neither, by declaring or deleting the operations in the
  `public` section:

```cpp
class Copyable {
 public:
  Copyable(const Copyable& other) = default;
  Copyable& operator=(const Copyable& other) = default;
};

class MoveOnly {
 public:
  MoveOnly(MoveOnly&& other) = default;
  MoveOnly& operator=(MoveOnly&& other) = default;
};

class NotCopyableOrMovable {
 public:
  NotCopyableOrMovable(const NotCopyableOrMovable&) = delete;
  NotCopyableOrMovable& operator=(const NotCopyableOrMovable&) = delete;
};
```

- These may be omitted only when obvious: a class with no `private` section
  (its members decide), or a class whose base is clearly not copyable or
  movable. Declaring or deleting one copy (or move) operation makes the other
  one non-obvious: declare or delete both.
- If you provide an assignment operator, also provide the matching
  constructor.
- Support copy/move only when its meaning is clear and it has no unexpected
  cost. Define move operations for copyable types only when they are
  significantly faster. Prefer designs where the defaulted operations are
  correct, and review them like any other code.
- To avoid slicing, make base classes abstract (protected constructor or
  destructor, or a pure virtual function). Avoid deriving from concrete
  classes.

**Structs vs. classes**

- Use `struct` only for passive data carriers: all fields public, no
  invariants between fields; constructors and helpers must not enforce
  invariants. Everything else is a `class`. When in doubt, use `class`.
- `struct` may be used for stateless types (traits, metafunctions, some
  functors).
- Prefer a `struct` with named fields over `std::pair` / `std::tuple`. Pairs
  and tuples are fine in generic code or when an existing API requires them.

**Inheritance**

- Prefer composition. Use inheritance for "is-a" relationships only.
- All inheritance **must** be `public`; instead of private inheritance, hold
  a member.
- Data members **must** be `private`; use `protected` only for member
  functions subclasses need.
- Overrides of virtual functions and destructors **must** have exactly one of
  `override` or `final`, and **must not** repeat `virtual`.
- Multiple inheritance is allowed; multiple *implementation* inheritance is
  strongly discouraged. `final` may mark classes not meant as bases.

**Operator overloading**

- Overload operators only when the meaning is obvious and matches the
  built-in operator. Define them only for your own types, in the same header,
  `.cc` file and namespace as the type. Avoid operator templates.
- If you define an operator, define the related ones consistently.
- Prefer non-member functions for non-modifying binary operators.
- For equality, define a non-member `operator==` and document what equal
  means. Define `operator<=>` only for an obvious ordering, consistent with
  `==`. Prefer not to overload the other comparison operators.
- Prefer operators over named equivalents (`==` over `Equals()`, `=` over
  `CopyFrom()`), but do not add operators just because a library expects
  them (use a custom comparator for `std::set` instead of inventing `<`).
- **Must not** overload `&&`, `||`, `,` (comma) or unary `&`.
- **Must not** define user-defined literals (`operator""`) or use any,
  including the standard library's (`"abc"sv`, `10ms`).

**Access control**

- Data members **must** be `private` unless they are constants. Exception:
  data members of a test fixture defined in a `.cc` file may be `protected`.

**Declaration order**

- Sections in the order `public:`, `protected:`, `private:`; omit empty ones.
- Within a section: types and type aliases (`using`, `enum`, nested classes,
  `friend` types); (structs only) non-static data members; static constants;
  factory functions; constructors and assignment operators; destructor; all
  other functions; all other data members.
- **Do not** put large method definitions inline in the class definition.

## 6. Functions

**Inputs and outputs**

- Prefer return values over output parameters.
- Return by value, else by reference. Return a raw pointer only if it can be
  null.
- Parameters:
  - required inputs: values or `const` references;
  - required outputs and in/out: references;
  - optional by-value inputs: `std::optional`;
  - optional inputs that would be references: `const` pointers;
  - optional outputs and in/out: non-`const` pointers.
- Avoid reference parameters that must outlive the call. If a parameter is
  retained, pass it by pointer and document the lifetime and non-null
  requirements, or copy it.
- Put input-only parameters before output parameters; do not add new
  parameters at the end just because they are new.

**Short functions**

- Prefer small, focused functions. Above about 40 lines, consider splitting
  if it does not harm the structure.

**Overloading**

- Overload only when a reader at the call site does not need to know which
  overload is chosen: no semantic differences between variants.
- Document the overload set with one umbrella comment before the first
  declaration.
- Consider `std::string_view` instead of `const std::string&` +
  `const char*` overloads.

**Default arguments**

- Allowed on non-virtual functions when the default always has the same
  value.
- **Must not** be used on virtual functions, or where the default can
  evaluate differently (`void f(int n = counter++);`).
- When in doubt, use overloads.

**Trailing return types**

- Use the ordinary `int Foo(int x);` form. Use trailing return types only
  where required (lambdas) or where they make a complicated template type
  much more readable.

## 7. Ownership and references

**Smart pointers**

- Prefer one fixed owner for each dynamically allocated object; keep
  ownership with the code that allocated it. Pass others a copy, or a pointer
  or reference without ownership.
- Use `std::unique_ptr` to transfer ownership:
  `std::unique_ptr<Foo> FooFactory();`, `void FooConsumer(std::unique_ptr<Foo> ptr);`.
- **Do not** design for shared ownership without a very good reason (for
  example avoiding expensive copies of an immutable object:
  `std::shared_ptr<const Foo>`). If shared, use `std::shared_ptr`.
- **Never** use `std::auto_ptr`.

**Rvalue references**

Use `&&` only for:

- move constructors and move assignment operators;
- `&&`-qualified methods that logically consume `*this` (for an ordinary
  parameter that is consumed, pass by value instead);
- forwarding references with `std::forward`;
- overload pairs like `Foo&&` / `const Foo&` when there is evidence of a
  performance gain.

**Friends**

- `friend` classes and functions are allowed within reason, usually defined
  in the same file (for example a `FooBuilder`, or a unit test). Prefer
  interaction through public members.

## 8. Exceptions, RTTI and casts

**Exceptions**

- **Do not** use C++ exceptions: no `throw`, `try`/`catch`,
  `std::exception_ptr` or `std::nested_exception` in project code. The only
  exception is the Thrift boundary described in waiver
  [W1](#project-waivers).
- Report errors with return values (`std::optional`, or the project's result
  type carrying the error).

**`noexcept`**

- Use `noexcept` when it is useful for performance and correct: an exception
  escaping the function would be a fatal error. Assume `noexcept` on move
  constructors is worthwhile; for other functions, only with evidence.
- Prefer unconditional `noexcept`; if conditional, keep the condition simple.

**RTTI**

- Avoid `typeid` and `dynamic_cast` outside unit tests. Prefer virtual
  methods, or double dispatch (Visitor) for work that belongs outside the
  object.
- `dynamic_cast` may be used when the program logic guarantees the dynamic
  type.
- **Do not** write type-based decision trees (`if (typeid(*d) == typeid(D1))
  ... else if ...`) and **do not** hand-implement RTTI substitutes (type
  tags).

**Casts**

- **Must not** use C-style casts (`(int)x`), except casts to `void`.
  `T(x)` is allowed only when `T` is a class type.
- Use the first that correctly applies:
  1. brace initialization for arithmetic conversions: `int64_t{x}` (does not
     compile if information would be lost);
  2. a function-style cast to a class type: `std::string(view)`;
  3. `static_cast` for value conversions, explicit up-casts, and down-casts
     where you are sure of the dynamic type;
  4. `const_cast` to remove `const` (see [§10](#10-const-constexpr-and-integer-types));
  5. `reinterpret_cast` for unsafe pointer/integer conversions, only if you
     understand the aliasing rules; consider `std::bit_cast` on the value
     instead;
  6. `std::bit_cast` to reinterpret the bits of a value of the same size.
- `dynamic_cast`: see RTTI above.

## 9. Streams and output

- Use streams only when they are the best tool: ad-hoc, local,
  human-readable I/O for developers. If the codebase has an established tool
  (the project's logger and output functions), use it instead of
  `std::cerr`, `std::clog` or `std::stringstream`.
- Avoid streams for I/O that faces users or handles untrusted data.
- If you use streams, avoid their stateful parts (`imbue()`, `xalloc()`,
  `register_callback()`) and manipulators/format flags; format explicitly
  (`std::format`).
- Overload `<<` only for value types, writing the user-visible value. For
  debugging internals, use a named function such as `DebugString()`.
- For printing numbers, use type-safe formatting (`std::format`) rather than
  the `printf` family.

## 10. const, constexpr and integer types

**Increment and decrement**

- Use prefix `++i` / `--i` unless you need the postfix result.

**`const`**

- Use `const` in APIs wherever it is meaningful and accurate:
  - parameters not modified through a reference or pointer: `const T&`,
    `const T*`;
  - **not** on by-value parameters in declarations;
  - methods are `const` unless they change the logical state, allow the
    caller to change it, or cannot safely run concurrently.
- `const` on local variables is neither required nor discouraged.
- All `const` operations of a class **must** be safe to call concurrently
  with each other, or the class **must** be documented as thread-unsafe.
- Prefer `const int* p` over `int const* p`, but be consistent with the
  surrounding code.

**`constexpr`, `constinit`, `consteval`**

- Use `constexpr` for true constants and the functions that define them; use
  `constinit` to ensure constant initialization of non-constant variables.
- `consteval` may be used for code that must not run at run time.
- Do not complicate a function just to make it `constexpr`, and do not use
  `constexpr`/`consteval` to force inlining.

**Integer types**

- Of the built-in integer types, use only `int`. Use `<stdint.h>` exact-width
  types (`int16_t`, `int64_t`, ...) when a size matters, never `short`,
  `long` or `long long`. `size_t` and `ptrdiff_t` may be used where
  appropriate.
- Assume `int` is at least 32 bits and no more. Use `int64_t` for values that
  could ever reach 2^31, including in intermediate results. When in doubt,
  use a larger type.
- Write `int64_t`, not `std::int64_t`.
- **Do not** use unsigned types to say a value is never negative (use an
  assertion). Unsigned types are for bit patterns and modular arithmetic.
- Containers that return sizes use a type large enough for any use.
- Be careful with integer conversions and promotions; avoid mixing signed and
  unsigned. Prefer iterators and containers over pointers and sizes.

**Floating point**

- Use only `float` and `double` (IEEE-754 binary32/binary64). **Must not**
  use `long double`.

**Portability**

- Do not rely on features of one processor.
- Store memory addresses as integers only in `uintptr_t`.
- Use braced initialization for 64-bit constants:
  `int64_t my_value{0x123456789};`, `uint64_t my_mask{uint64_t{3} << 48};`.
- Move structured data in or out of the process with a serialization format,
  not by copying the in-memory representation.

## 11. Preprocessor macros

- Avoid macros, especially in headers. Use inline functions, enums, `const`
  variables and references instead. Do not use macros for conditional
  compilation except header guards.
- **Must not** use macros to define pieces of a C++ API.
- If a macro is needed:
  - do not define it in a `.h` file;
  - `#define` it right before use and `#undef` it right after;
  - do not `#undef` an existing macro to replace it; pick a unique name;
  - avoid macros that expand to unbalanced constructs, or document them;
  - prefer not to build names with `##`.
- A macro exported from a header (strongly discouraged) **must** have a
  globally unique name with the project prefix: `CC_ROUND(x)`.
- Use `nullptr` for null pointers and `'\0'` for the null character, never
  `0` or `NULL`.
- Prefer `sizeof(varname)` over `sizeof(type)`; use `sizeof(type)` only for
  code not tied to a variable (for example an external data format).

## 12. Type deduction

- Use type deduction only when it makes code clearer or safer for a reader
  who does not know the project, never just to avoid writing a type.
  `auto x = std::make_unique<Foo>()` is clear; `auto x = MyWidgetFactory()`
  probably is not.
- **Function template argument deduction**: almost always fine.
- **Local variables**: use `auto` to remove obvious or irrelevant type
  information (iterators, `make_unique`). Prefer structured bindings for
  map elements. Avoid `decltype(auto)` when something simpler works.
- **Return type deduction**: only for functions or lambdas with very few
  `return` statements, little code and narrow scope. Public functions in
  headers should almost never deduce their return type.
- **Parameter type deduction**: avoid it when you can name the type.
  **Must not** use `auto` parameters in non-lambda functions; use named
  template parameters. In lambdas that need the parameter's type, use
  `[]<typename T>(T x)` rather than `decltype(x)`.
- **Structured bindings**: encouraged where they give meaningful names
  (pairs, tuples, map elements). If a binding's name differs from the struct
  field, comment it: `auto [/*field_name1=*/bound_name1, ...] = ...`.
- **Class template argument deduction (CTAD)**: use only with templates that
  provide at least one explicit deduction guide (all `std` templates count as
  opted in).
- **Designated initializers**: only in C++20 form, in the same order as the
  fields are declared.

## 13. Lambdas, templates, concepts, modules, coroutines

**Lambdas**

- Use lambdas where appropriate.
- Prefer explicit captures when the lambda may escape the current scope:
  `[&foo]`, not `[&]`.
- Use `[&]` only when the lambda's lifetime is obviously shorter than all
  captures.
- Use `[=]` only for short lambdas with an obvious set of captures, and never
  to capture `this` implicitly (capture `this` explicitly or use `[&]`).
- Use init captures only to capture from the enclosing scope, not to
  introduce new names or change meanings; declare a variable and capture it,
  or write a function object.

**Template metaprogramming**

- Avoid complicated template programming (recursive instantiation, type
  lists, expression templates, SFINAE tricks). If used, keep it in a few
  low-level components, hide it from user-facing headers, comment it well,
  and make the compiler errors understandable.

**Concepts and constraints**

- Use them sparingly, only where a template would have been used before
  C++20.
- Prefer standard concepts over type traits (`std::integral`, not
  `std::is_integral_v`). Prefer `requires(Concept<T>)`; avoid
  `template <Concept T>` and `std::enable_if`.
- Do not re-implement existing concepts or traits.
- New `concept`s should be rare and internal to a library, not at API
  boundaries. Do not define concepts that only repeat the function body, or
  that the compiler cannot verify.

**Modules**

- **Must not** use C++20 modules.

**Coroutines**

- Use coroutines only through a coroutine library approved for the project.
  **Do not** write your own promise or awaitable types.

## 14. Libraries and extensions

**Standard library features not allowed**

- **Must not** use `<ratio>`.
- **Must not** use `<cfenv>` / `<fenv.h>`.
- `<filesystem>` **is allowed**, with the non-throwing overloads only
  (waiver [W2](#project-waivers)).

**Third-party libraries**

- First use the library the codebase already uses for that kind of problem
  (the choices are listed in [libraries.md](libraries.md)). If there is none,
  prefer the C++ standard library (except as restricted here), then existing
  code in the project, then a new third-party library.
- Follow the project's policy for adding third-party code (a new library is a
  decision recorded in [libraries.md](libraries.md)).

**Nonstandard extensions**

- **Must not** use compiler extensions: `__attribute__`, intrinsics such as
  `__builtin_prefetch` or SIMD, `#pragma` (including `#pragma once`), inline
  assembly, `__COUNTER__`, `__PRETTY_FUNCTION__`, statement expressions,
  variable-length arrays, `alloca()`, `a ?: b`.
- Portability wrappers built on extensions are allowed if they come from one
  designated project-wide portability header.

## 15. Other features

**Aliases**

- Prefer `using` over `typedef`.
- Put an alias in a public API only if clients are meant to use it, and
  document its intent (is it guaranteed to stay the same type, or only
  compatible in limited ways?).
- Local convenience aliases are fine in `.cc` files, function bodies,
  `private` sections and internal namespaces. **Do not** put namespace
  aliases in public APIs.

**Switch statements**

- A `switch` not on an enumerated value **must** have a `default` case. If
  `default` should never run, treat it as an error.
- Fall-through between case labels with code in between **must** be marked
  with `[[fallthrough]];`. Consecutive labels with no code need no marking.

## 16. Inclusive language

- In all code, names and comments, use inclusive language: avoid terms such
  as master/slave, blacklist/whitelist, redline (use for example
  primary/replica, denylist/allowlist).
- Use gender-neutral language: they/them for people of unspecified gender,
  it/its for software and things.

## 17. Naming

**Choosing names**

- Names make the purpose clear to a new reader. Descriptiveness grows with
  the scope of visibility: a header-level function names its library; a loop
  index may be `i`.
- Do not repeat information obvious from the immediate context.
- Minimize abbreviations unknown outside the project. **Do not** abbreviate
  by deleting letters inside a word (`cstmr_id`). Capitalize abbreviations as
  one word: `StartRpc()`, not `StartRPC()`. Universally known ones (`i`, `T`,
  abbreviations listed in Wikipedia) are fine.

**Summary**

| Entity | Style | Example |
|---|---|---|
| Files | lowercase, `_` (or the project's existing `-`) | `report_hash.cc`, `report_hash.h`, `report_hash_test.cc` |
| Types (class, struct, alias, enum, type template parameter), concepts | PascalCase | `UrlTable`, `UrlTableError` |
| Variables, parameters, struct data members | snake_case | `table_name` |
| Class data members | snake_case + trailing `_` | `table_name_` |
| Constants (`constexpr`/`const`, fixed for the program; all such statics) | `k` + PascalCase | `kDaysInAWeek` |
| Functions | PascalCase | `AddTableEntry()` |
| Accessors and mutators | may be snake_case | `count()`, `set_count(int count)` |
| Namespaces | snake_case; top level `cc` (W3) | `cc::report` |
| Enumerators | like constants | `kOutOfMemory` |
| Non-type template parameters | like variables or constants | `kMaxAttempts` |
| Macros (avoid) | UPPER_CASE with project prefix | `CC_ROUND` |

Details:

- **Files**: `.cc` for C++ sources, `.h` for headers, `.inc` for textual
  inclusion. Do not reuse names that exist in `/usr/include` (`db.h`). Make
  names specific (`http_server_logs.h`, not `logs.h`); a class `FooBar`
  usually lives in `foo_bar.h` / `foo_bar.cc`. Test files end in `_test.cc`.
- **Types**: no underscores.
- **Constants**: underscores only where capitalization cannot separate
  (`kAndroid8_0_0`). Optional for automatic variables; never use `k` for a
  value that differs between calls.
- **Functions**: class- or namespace-scope constants that are part of an API
  and meant to look like functions are named like functions.
- **Namespaces**: top-level namespaces are unique and owned by one project;
  code in a namespace lives in directories of the same name. Nested
  namespaces avoid well-known top-level names (`std`). This project's
  top-level namespace is `cc` (W3).
- **Enumerators**: `kEnumName`, never `ENUM_NAME`.
- **Aliases**: named by the same principles, for the context where the alias
  is defined.
- **Exceptions**: something analogous to an existing C or C++ entity may
  follow that entity's convention (`bigopen()` like `open()`,
  `sparse_hash_map` like STL, `LONGLONG_MAX` like `INT_MAX`).

## 18. Comments

**General**

- The best code is self-documenting; good names beat comments. Comment for
  the next reader.
- Use `//` (or `/* */`) consistently; `//` is the norm.
- Write comments as readable prose with correct capitalization,
  punctuation, spelling and grammar. End-of-line comments may be less formal.

**File comments**

- Start each file with the project's license boilerplate. New files usually
  do not get a copyright notice or author line; consider removing an author
  line when you change a file significantly.
- If a file declares several related user-facing abstractions, add a comment
  describing the collection (and what does not belong there). If a `.h` file
  has a file comment, its `.cc` and `_test.cc` files do not need one; a `.cc`
  file without a header that defines several things does.

**Classes and structs**

- Every non-obvious class or struct gets a comment saying what it is for and
  how to use it, including its synchronization assumptions and the rules for
  use from several threads. A short usage example is often helpful.
- Comments about using the class go with the interface (`.h`); comments
  about how it works go with the implementation (`.cc`).

**Functions**

- Almost every function declaration (including private ones and those in
  `.cc` files) gets a comment right before it, unless it is simple and
  obvious (simple accessors). Write it with the implied subject "This
  function": "Opens the file", not "Open the file".
- Mention what applies: inputs and outputs (argument names in backticks);
  whether the object keeps reference or pointer arguments after the call;
  for each pointer argument whether it may be null and what null means; what
  happens to the previous state of output arguments (appended or
  overwritten); performance implications.
- Do not be verbose or state the obvious. For overrides, describe only what
  is specific to the override. For constructors and destructors, describe
  what they do with arguments and what cleanup happens; skip trivial ones.
- At the definition, explain anything tricky about how the function works
  (the steps, why this approach, why a lock is needed only in part). Do not
  repeat the declaration comment.

**Variables**

- Class data members: comment invariants, special values (for example
  "-1 means unknown") and lifetime rules not clear from type and name.
- Every global variable gets a comment saying what it is, what it is for and,
  if unclear, why it is global.

**Implementation comments**

- Comment tricky, non-obvious, interesting or important code, before the
  block.
- When a function argument's meaning is not obvious at the call site, prefer
  in this order: a named constant; an `enum` instead of a `bool`; an options
  struct; a named variable for a complex expression; as a last resort, a
  comment at the call site: `CalculateProduct(values, options,
  /*completion_callback=*/nullptr);`.
- **Do not** describe what the code literally does; explain why, or make the
  code self-describing.

**TODO comments**

- Use `TODO` for temporary, short-term or good-enough-for-now code:
  `// TODO(<issue link, name or e-mail>): <what to do>`.
- A "do it later" `TODO` names a specific date or a specific event.

## 19. Formatting: lines, indentation, characters

- **Line length**: at most **80 characters**. Allowed longer: a comment line
  that cannot be split without harming readability or links (a long URL or
  command); a string literal that cannot easily be wrapped (URLs, embedded
  languages, multi-line literals with significant newlines such as help
  texts; outside tests, put such literals at namespace scope near the top of
  the file); `#include` lines; header guards; using-declarations.
- **Indentation**: spaces only, **2 spaces** per level. No tabs.
- **Non-ASCII characters**: rare, and always UTF-8. Hex escapes are fine and
  encouraged where they help (`"﻿"`). Avoid the `u8` prefix. **Do not**
  use `char16_t`, `char32_t` or `wchar_t`.
- **Trailing whitespace**: never add it. Remove it on lines you change anyway.
- **Vertical whitespace**: use blank lines sparingly, like paragraph breaks
  between related chunks. No blank lines at the start or end of a block.

## 20. Formatting: functions and calls

**Declarations and definitions**

```cpp
ReturnType ClassName::FunctionName(Type par_name1, Type par_name2) {
  DoSomething();
}

ReturnType ClassName::ReallyLongFunctionName(Type par_name1, Type par_name2,
                                             Type par_name3) {
  DoSomething();
}

ReturnType LongClassName::ReallyReallyReallyLongFunctionName(
    Type par_name1,  // 4 space indent
    Type par_name2,
    Type par_name3) {
  DoSomething();  // 2 space indent
}
```

- Return type on the same line as the name; if they do not fit together,
  break between them without indenting.
- The opening parenthesis is on the same line as the name; no space before it
  and no spaces inside the parentheses.
- The opening brace ends the last line of the declaration, after one space.
  The closing brace is on its own line or on the same line as the opening
  brace.
- Align wrapped parameters with the first one, or put them all on following
  lines with a 4-space indent.
- Omit a parameter name only if the parameter is unused and its meaning is
  obvious; otherwise comment it out in the definition:
  `void Circle::Rotate(double /*radians*/) {}`.
- Attributes go first, before the return type: `[[nodiscard]] bool IsOk();`.

**Lambdas**

- Format parameters and bodies like functions, capture lists like other
  lists. No space between `&` and the name in a capture: `[&x]`.
- Short lambdas may be written inline as arguments.

**Function calls**

- One line if it fits. Otherwise align wrapped arguments with the first
  argument, or start all arguments on the next line with a 4-space indent.
  Use the fewest lines, with several arguments per line.
- No spaces after `(` or before `)`.
- If an argument is complex, put it in a well-named variable, or on its own
  line with a comment. Arguments with a structure (a matrix) may be laid out
  to show it.

```cpp
bool result = DoSomething(averyveryveryverylongargument1,
                          argument2, argument3);

    bool result = DoSomething(
        argument1, argument2,  // 4 space indent
        argument3, argument4);
```

**Braced initializer lists**

- Format exactly like a function call in the same place (treat `{}` as the
  call's parentheses; with no name before it, assume a zero-length name).

```cpp
return {foo, bar};
SomeType variable{
    some, other, values,
    SomeOtherType{"Slightly shorter string",
                  some, other, values}};
```

**Floating-point literals**

- Always with a radix point and digits on both sides: `1.0f`, `-0.5`,
  `1248.0e6`; not `1.f`, `-.5`, `1248e6`. Initializing a floating-point
  variable with an exact integer literal is fine.

## 21. Formatting: statements and expressions

**Loops and branches**

- One space between the keyword, the parenthesized condition and the brace:
  `if (condition) {`. No spaces inside the parentheses. One space after each
  `;` inside `for (...)`.
- Controlled statements go in braces, with a line break after `{` and before
  `}`. `else` goes on the same line as the closing brace: `} else {`.
- Allowed but discouraged: omitting braces when the whole statement fits on
  one line (`if (x == kFoo) return new Foo();`) or on two lines (condition
  line + one statement). Never for `if ... else` or `do ... while`.
- `case` blocks may use braces, placed as below. Empty loop bodies use `{}`
  or `continue`, never a lone `;`.

```cpp
if (condition) {
  DoOneThing();
} else if (int a = f(); a != 3) {
  DoAThirdThing(a);
} else {
  DoNothing();
}

for (int i = 0; i < 10; ++i) {
  RepeatAThing();
}

switch (var) {
  case 0: {  // 2 space indent
    Foo();   // 4 space indent
    break;
  }
  default: {
    Bar();
  }
}

while (condition) continue;
```

**Pointers and references**

- No spaces around `.` or `->`; no space after unary `*` or `&`:
  `x = *p; p = &x; x = r->y;`.
- In types, no space before `*` / `&`, one space before the name:
  `char* c;`, `const std::string& str;`, `std::vector<char*>`.
- **Must not** declare several variables in one declaration if any has `*`
  or `&` (`int x, *y;`). `int x, y;` is allowed.

**Boolean expressions**

- When wrapping, put operators consistently at the end of lines (common) or
  at the start. Use `&&`, `||`, `!`, never `and`, `or`, `not`. Extra
  parentheses are fine where they help.

**Return values**

- No needless parentheses: `return result;`, not `return (result);`.
  Parentheses only where you would use them in `x = expr;`.

**Variable initialization**

- `=`, `()` and `{}` are all allowed.
- A non-empty `{...}` prefers an `std::initializer_list` constructor:
  `std::vector<int> v(100, 1);` (100 ones) vs. `std::vector<int> v{100, 1};`
  (two elements). Use parentheses to avoid it.
- `{}` prevents narrowing (`int pi{3.14};` does not compile), which is often
  useful.

**Preprocessor directives**

- `#` always starts at column 0, even inside indented code. Spaces after `#`
  for nested directives are allowed.

## 22. Formatting: classes, namespaces, whitespace

**Classes**

```cpp
class MyClass : public OtherClass {
 public:      // 1 space indent
  MyClass();  // 2 space indent
  explicit MyClass(int var);
  ~MyClass() {}

  void SomeFunction();
  void set_some_var(int var) { some_var_ = var; }
  int some_var() const { return some_var_; }

 private:
  bool SomeInternalFunction();

  int some_var_;
};
```

- The base class on the same line as the class name (within 80 columns).
- `public:`, `protected:`, `private:` indented 1 space, in that order; a
  blank line before each except the first (optional in small classes); no
  blank line after them.

**Constructor initializer lists**

```cpp
MyClass::MyClass(int var) : some_var_(var) {
  DoSomething();
}

MyClass::MyClass(int var)
    : some_var_(var), some_other_var_(var + 1) {
  DoSomething();
}

MyClass::MyClass(int var)
    : some_var_(var),             // 4 space indent
      some_other_var_(var + 1) {  // lined up
  DoSomething();
}
```

- All on one line, or break before `:` with a 4-space indent; when the list
  spans lines, one member per line, aligned.

**Namespaces**

- The contents of a namespace are **not** indented.

**Horizontal whitespace**

- Two spaces before end-of-line comments: `int i = 0;  // Comment.`
- A space before every `{` that opens a block; no space before `;`.
- Spaces inside braced lists are optional but symmetric: `{0}` or `{ 0 }`.
- Spaces around `:` in inheritance and initializer lists.
- Inline one-line bodies: `void Reset() { baz_ = 0; }`; empty braces `{}`
  have no space inside.
- A space after `if`, `while`, `for`, `switch`; around `else`; before and
  after `:` in range-based `for`. No space before `:` in `case 1:`; a space
  after it if code follows.
- Spaces around assignment operators. Spaces around other binary operators
  are usual, but may be removed around factors: `v = w*x + y/z;`. No space
  between a unary operator and its operand: `-5`, `++x`, `!y`.
- No spaces inside `<` `>` or before `<`, and none between `>` and `(` in a
  cast: `std::vector<std::string> x;`, `static_cast<char*>(x)`.

## 23. Tools

- `cpplint` may be used to find style errors. It is an external tool and is
  not added to this repository. It has false positives and false negatives;
  this guide decides.

## 24. Existing non-conformant code

- Code that was not written to this guide (code copied unchanged from the
  Python repository, code generated by the Thrift compiler, third-party
  headers) is not changed to follow it.
- When you modify code written to other conventions, you may follow its local
  conventions to stay consistent within that code.
- New code that calls such code still follows this guide.

## 25. Checklist

Before finishing a change, check:

- [ ] C++20, no C++23 features, no compiler extensions, no modules.
- [ ] No exceptions outside the Thrift boundary (W1); `std::filesystem`
      only through `std::error_code` overloads (W2); no `<ratio>`, `<cfenv>`;
      no user-defined literals.
- [ ] Headers: `.h`, self-contained, `#define` guard
      `CC_<PATH>_<FILE>_H_`, include what you use, include order.
- [ ] Everything in namespace `cc::<library>` (W3); no `using namespace`;
      internal linkage for file-local code.
- [ ] Static/global objects are trivially destructible.
- [ ] Single-argument constructors and conversion operators are `explicit`;
      copy/move support is declared.
- [ ] Data members `private` (classes) with trailing `_`; `override` on
      overrides.
- [ ] Integer types: `int` or `<stdint.h>` types; no unsigned for
      "non-negative".
- [ ] Casts: no C-style casts.
- [ ] Naming table followed (`.cc`/`.h` files, PascalCase types and
      functions, snake_case variables, `kConstants`).
- [ ] Comments on non-obvious classes and function declarations.
- [ ] 80 columns, 2-space indent, no tabs, no trailing whitespace, braces
      and spacing as in §19–22.
